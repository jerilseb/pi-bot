# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project overview

`pi-bot` is a small Telegram bot that bridges one Telegram chat to a Pi SDK session, with an optional terminal UI (`npm run tui`) on the same conversation. It uses long polling, Pi model refs (for example OpenRouter or OpenAI Codex), optional voice features (Google GenAI / ElevenLabs), and local Pi extensions. No skills are loaded; when one is needed the user asks the agent to read its SKILL.md.

Terms, kept apart in code, comments and prompts:

- **Scheduled task**: an entry in `files/cron-jobs.json` that fires on a schedule (`once`, `interval` or `cron`). "Cron job" means the same thing: the user may say either, and the code calls it that (`CronJob`, `cron-store.ts`, `"cronJobs"`). A scheduled task is never called a job anywhere else, or a background job.
- **Background session** and **background run**: the Pi session scheduled tasks and the heartbeat run in, and one run in it, with a fresh transcript per run. A background run is a scheduled task firing, a heartbeat, or the report of a background job one of them started.
- **Background job**, or just **job**: a background bash command or a sub-agent job, which the agent starts with `background_bash_start` or `subagent_run` from either session, and which reports back when it finishes (`JobRegistry`, the `job` events, the progress messages, `/jobs`).
- **Background bash session**: the shell process behind a background bash job, the `session_id` of the `background_bash_*` tools. It is not a Pi session.

Key files:

- `main.ts` — entrypoint/orchestrator: constructs the runtimes and sessions, the agent core, the Telegram channel attached to it and, with `ENABLE_TUI`, the socket server terminals attach through; wires the modules together, and owns the startup banner, post-restart tasks, and shutdown (which drains every channel, then closes the socket). Keep it to wiring and lifecycle; new behavior belongs in a module.
- `src/contract.ts` — the contract between the agent core and the interfaces that use it ("channels"), types only: `AgentCore` (submit, command, commands, choose, stopJob, beginIngestion, attach, snapshot; every call that answers is async, so the core can be in another process), `Channel` (with its capabilities, own commands and own `/status` settings), the ordered `CoreEvent` stream (turns, SDK events, job snapshots, closed menus, notices, state), deliveries (files, voice notes, menus, background reports) with receipts, and `PromptOrigin`. `src/core.ts` — `LocalCore`, the in-process `AgentCore`: owns the prompt queue, the commands and the open menus, fans events and deliveries out to the attached channels, and records each channel's last action to decide what an event pings (a reply, or anything sent during a chat turn, pings the channel the turn's input came from; anything unprompted pings the channel used within `ACTIVE_WINDOW_MS`, else every durable one). Work the bot gives itself (heartbeat, cron, post-restart, job reports) enters through `core.enqueue`. `core.toolHost` is how the agent's tools reach the user; `main.ts` installs it with `setToolHost` (`src/tool-host.ts`), and tests install a fake. Model replies and the bot's own text (commands, `/status`, usage, restart checks, notices) are Markdown (`src/markdown.ts` escapes what the bot did not write); each channel renders it, Telegram through `markdown.ts`, the terminal through Pi's renderer. `files/system.md` asks the model for the subset both render the same way.
- `src/prompt-queue.ts` — the queue every prompt goes through regardless of origin (user input, heartbeat, cron, post-restart, background-bash report, sub-agent report) plus the serial worker. It sends nothing itself: `handleIncoming` returns a `SubmitResult` (queued, steered, or rejected) for the channel to show, and a turn is emitted as `turn_start`, every SDK event (`agent`, with the turn's ID), and `turn_end` with the reply or error. User input steers an active chat run; background runs, job reports and startup/finishing races queue normally. A background run's reply is a `report` delivery through the outbox. `src/prompt-steering.ts` holds the prompts steered into a run until it finishes, so their attachments outlive the message; Pi delivers each one within the run, even one that lands after the agent last checked its queue.
- `src/config.ts` — env vars, paths, models, and all non-secret tuning. `src/config-validation.ts` — the startup config checks, shared by `main.ts` and the smoke check so the startup and restart gates cannot drift apart.
- `src/pi-session.ts` — Pi SDK runtime + `AgentSession` wrapper (session reuse: the chat resumes the transcript `sessions/current-chat` names, which `/new` and `start_new_session` delete; `history()`, the conversation as the chat would resume it, without starting an agent, for `snapshot()`; extension wiring; stream collection; an event hook subscribed to every `AgentSession` it creates, since a model switch, `/new` and each session-per-prompt run replace it) and `runWorkerPrompt`, the one-shot worker session sub-agents run in. Retrying a failed model request is Pi's own, set by `"retry"` in `files/settings.json`.
- `src/session-notes.ts` — notes the bot writes into transcripts so Pi knows what happened outside its turns (restarts, model changes, aborts, messages the background session sent), and the unclean-exit check.
- `src/chat-session.ts` — the single chat's state and explicit session disposal (no idle timeout).
- `src/channels/telegram/` — the Telegram channel. `channel.ts` (`TelegramChannel`) turns core events into sends through one ordered queue: per chat turn a typing indicator and tool notifications, then the reply once they have finished; a background turn shows nothing until what it sent arrives as deliveries. Input from another channel (a terminal) is mirrored silently under a "🖥", with its attachments' names; that turn gets no typing indicator and its tool calls go out silently. It shows its own submit feedback (steering ack, queue full), renders core menus as inline keyboards (`choices.ts`, callback data `ch:<id>:<index|cancel>`) and edits every copy when one closes, edits a placeholder notice into its outcome (`replaceTelegramMessage`, which sends it anew when the edit is refused), and uploads files and voice notes (`media.ts`, within Telegram's size limits). `markdown.ts` — Markdown → Telegram HTML (headings bold, lists as bullet lines, tables as `<pre>`, code, links, quotes and emphasis as Telegram's tags). `commands.ts` — Telegram's own commands (`/start`, and the display settings `/toolcalls`, `/transcripts`, `/subagent_toolcalls`), whose menus (`tool-call-menu.ts`, `transcript-menu.ts`, `subagent-tool-call-menu.ts`) use `callback-menu.ts`, the inline-keyboard lifecycle; it also orders Telegram's command menu (`inMenuOrder`, `/abort` first, as in claude-bot), interleaving the core's commands with its own, so a new command needs a place in `MENU_ORDER` or goes last. `jobs.ts` keeps a live progress message per job the chat started, from the core's `job` snapshots: `job-progress.ts` paces the edits (at most one per `JOB_PROGRESS_MIN_EDIT_MS`, a heartbeat every `JOB_PROGRESS_UPDATE_MS`, and a gate shared by all live messages spacing routine edits `JOB_PROGRESS_GLOBAL_MIN_GAP_MS` apart; with no Telegram 429 handling, those intervals and the wait after a failed edit are the only rate protection), `bash-progress.ts` and `subagent-progress.ts` render them, and `job-stop-action.ts` turns a Stop tap into `core.stopJob`. A job's last write joins the send queue, so its report never lands before the message shows the outcome. `polling.ts` — the long-polling loop. `telegram.ts` — Bot API transport plus the HTML fallback ladder; `telegram-html.ts` — escaping, sanitizing, tag-aware splitting (pure). `tool-notification-batch.ts` — coalesces a turn's tool-call notifications in the `toolCalls` mode (`collapsed` edits one expandable message per turn, `stream` sends one per batch, `off` drops them); `tool-notifications.ts` — formats one event and renders the collapsed block (pure). `inbound.ts` — message/file/photo/audio ingestion. `types.ts` — Bot API payloads. The channel takes its settings (`toolCalls`, `subagentToolCalls`, `showTranscripts`) as options, so tests never read `files/settings.json`.
- `src/channels/socket/` — the terminal UI's socket, the server's half. `protocol.ts` is the wire protocol: the AgentCore contract as JSONL (`jsonl.ts`, LF-only framing as in Pi's RPC mode): a `hello` answered with the channel's ref, the commands and a snapshot; requests and responses by ID; events; deliveries answered with receipts. Image bytes and a streaming update's repeated partial never cross. `server.ts` (`SocketServer`) listens on `tuiSocketPath()` in a directory private to the user, removes a stale socket, refuses one another bot still answers on, and makes each connection a `SocketChannel` (`channel.ts`, `tui:<n>`): attached on its hello, it holds events until the welcome is written, coalesces streaming updates, drops a client that falls `TUI_CLIENT_BUFFER_MAX_BYTES` behind, times out receipts, runs one connection's submits in order, and turns away attachments that do not exist.
- `src/tui/` and `tui.ts` — the terminal UI client, a separate process (`npm run tui`). `remote-core.ts` (`RemoteCore`) implements `AgentCore` over the socket: hello on every connection, the welcome handed over before that connection's events, reconnect with backoff, calls failing at once while disconnected. `app.ts` (`TerminalApp`) is the terminal as a `Channel`: Pi's TUI in the main screen (`TuiMainScreen`), the editor (`prompt-editor.ts`: a line above and below, and a `❯` before the text in the column of the chat prompts' own), the working spinner on a line above it while the chat is busy, as Pi's is (`working-indicator.ts`), the chat (`chat-view.ts`, mapped from session events the way Pi's interactive mode maps them, history from the snapshot, and kept short with its own components: `user-prompt.ts`, a prompt beside a `❯` on a band across the width, a shade off the terminal's own background (asked with OSC 11 at startup; Pi's prompt colours when it does not answer, `promptBand` in `style.ts`), others' input labelled; `tool-call.ts`, a tool call as one row, its mark, name, first argument and what it came to (`tool-summary.ts`, pure: Pi's own tools from the shape of their results, the web tools by how many lines they returned, any other by its output's first line), a failure's reason under it; `assistant-reply.ts`, the reply as Markdown with thinking shown only while under way; `custom-note.ts`, a note the bot wrote into the transcript as a `── Bot restarted ──` divider, titled by its kind for the user, its text on `/expand`; `chat-log.ts`, a blank row between blocks except between tool calls; the bot's own prompts as one line; `/expand` opening output, thinking and notes in full), live jobs (`jobs.ts`), the footer (`footer.ts`), menus in the editor's place (`picker.ts`), the bell for pings, and its own commands (`/attach`, `/jobs`, `/expand`, `/quit`). Model replies are Markdown, so Pi's renderer draws them as they are. `style.ts` is its ANSI styles, which the chat's components use in place of Pi's theme. Nothing in `src/tui/` may run anything on import; `tui.ts` is the entry point and is never imported.
- `src/attachments.ts` — cleanup of the temp downloads behind a prompt's attachments; the core owns what a channel submits. `src/ingestion.ts` — ingestion tickets: a channel takes one before a slow download, `/abort` and `/new` make older ones stale, and the core turns a stale submit away. `src/outbound.ts` — the noop-sentinel check (`isSilentResponse`); sending is each channel's.
- `src/status.ts` — the /status layout in Markdown, rendered from a plain snapshot (pure, tested), with the interfaces attached and a section per attached channel's own settings; `commands.ts` gathers the snapshot. `src/format.ts` — plain-text helpers it and the usage reports share.
- `src/commands.ts` — the core's slash-command table (menu descriptions, `/help` lines, handlers). A handler answers through its `CommandContext`: `reply` sends Markdown to the channel that asked, or to every channel for a change they all need (`/new`, `/abort`, the restart checks); `status` sends a placeholder the same way ("Fetching usage...", "Running pre-restart checks...") and returns a handle whose `replace` sends the outcome, a notice tied to it by `replaces`, so a channel that can edit shows it in the placeholder's place (the tool host has the same `status`, for `restart_bot`); and `offer` opens a menu for the asking channel. `src/openai-usage.ts` and `src/elevenlabs-usage.ts` back `/openaiusage` and `/elevenlabsusage`. `src/choices.ts` — the menu lifecycle every channel shares (`ChoiceRegistry`): single use, first answer wins, Cancel, refusing while busy, stale options, expiry; a menu with a stable ID has a definition, so a copy from before a restart still works. `src/model-menu.ts` and `src/reasoning-menu.ts` are the `/models` and `/reasoning` menus (`models`, and `reasoning.<levels>` so a rebuilt menu has the levels it showed).
- `src/system-prompt.ts` — system prompt, and the memory and chat-settings blocks. `src/context-gist.ts` — the shared preferences gist (`CONTEXT_GIST_URL`), fetched once at startup. Each block is a named section of Pi's prompt, set on `event.systemPromptOptions.sections` in `before_agent_start`; never return `systemPrompt` there, which forces a whole prompt for the run, keeps the blocks out of the transcript and costs the conversation's cached prefix whenever one changes.
- `src/heartbeat.ts` — scheduled heartbeat controller. `src/cron.ts` + `src/cron-store.ts` — scheduled tasks; `src/scheduled-tasks.ts` — the agent's tools for them, registered only when `cronJobs` is on. Neither waits for the chat, only for the background run before it.
- `src/background-outbox.ts` — holds everything a background run sends the user (its report, an error, and the send_image/send_document/send_voice_note/send_menu tools, which take the session kind) until the chat has been idle — no turn running or queued, no user action from any channel — for `BACKGROUND_DELIVERY_COOLDOWN_MS` (5 min), and while no channel is attached. `deliverToChat` is the door: the chat session sends directly, the background session through the outbox. The chat-session note about a report is written when a channel's receipt says it was delivered, not when the run ends. Held messages are in memory only, go out in order, and are dropped on restart; `/status` shows how many are waiting.
- `src/background-bash.ts` — background shell sessions; `src/output-buffer.ts` bounds their output in memory and spills the full output to a temp file. `src/subagent.ts` — sub-agent jobs: concurrent worker sessions with their own transcripts under `sessions/subagent-sessions/`, registered only when `ENABLE_SUBAGENTS=true` in `.env`. Each task has its own abort as well as the job's, so one worker can be stopped while the rest of the job carries on. `src/job-registry.ts` — the lifecycle bookkeeping both share: IDs, the yield-then-background step, TTL pruning, cancellation, report routing back to the originating session, dropping a queued report once that session has read the finished result, and announcing the progress of every job the chat started as `job` events carrying plain snapshots (`BashJobSnapshot`, `SubagentJobSnapshot`): one as it starts, one per change (bursts coalesced to one per tick), an urgent one for the user's own stop, and a final one as it settles, before its report. No model call is involved; each channel paces its own updates (Telegram's progress messages are under `src/channels/telegram/`). A sub-agent job's message is a line per task while it runs, then a one-line summary with the task lines folded, since the agent's reply carries the results; with the `subagentToolCalls` setting on, each task also folds its worker's recent tool calls into a quote, replaced by its result when it finishes. Both kinds carry Stops: one for a command, one per unfinished sub-agent task, reaching the job through `core.stopJob`. A stop the user makes there reports to the agent, saying so; the agent's own `*_stop` tools and shutdown go through `JobRegistry.cancel()` and send no report. Background bash also has a wait tool (`background_bash_wait`, through `JobRegistry.waitFor`) that blocks the tool rather than the model; `src/steering-signal.ts` ends such a wait as soon as the user steers a message into that turn, so the message is not held until the wait times out. Sub-agent jobs have no wait tool on purpose: once a job is backgrounded the agent ends its turn and the report resumes it, so the chat is free while the workers run. `src/extension-models.ts` — model lookups shared by the tools that pin work to a model.
- `src/agent-envelope.ts` — shared layout for the internal prompts the bot sends itself (heartbeat, cron, post-restart, background-bash and sub-agent reports).
- `src/uploads.ts`, `src/voice.ts`, `src/speech.ts`, `src/menu-tool.ts` — the agent's tools for sending the user files, voice notes and menus, as deliveries through the tool host; the tool result summarises the receipts, and a tool errors when no channel took its delivery. Speech is synthesized only when an attached channel plays voice notes. A menu goes to every channel, and its answer comes back as the answering channel's user message, so it can steer. `src/session-switch-tool.ts` — `start_new_session`.
- `src/env-guard.ts` — blocks tool access to `.env` files. `src/util.ts` — shared helpers. `src/types.ts` — shared types (`IncomingPrompt`, `Attachment`). `src/tool-result.ts` — the plain-text tool result helper. `src/tool-call-description.ts` — a tool call as one line of plain text, for every interface.
- `src/restart-tool.ts`, `src/restart-flow.ts` (shared `/restart` + `restart_bot` gate), `src/pre-restart-checks.ts`, `src/post-restart-tasks.ts` — restart lifecycle.
- `extensions/` — local Pi extensions (web search, web fetch). The project root is loaded as a Pi package: `package.json` names this directory under `"pi"`, and Pi finds each extension in it.
- `files/` — persistent prompt/memory/heartbeat/schedule state, including `files/system.md` and `files/subagent.md`, the chat and worker system prompts (both checked in).
- `scripts/systemd.sh` — installs/removes the systemd `--user` unit. `scripts/smoke.ts` — the smoke check.

The dependency rule points one way: interfaces import the core, and nothing directly in `src/` may import `src/channels/` (or a future `src/tui/`). `tests/boundary.test.ts` enforces it. The core never branches on which channel it is talking to: what differs is a channel's declared capabilities, its own commands, and its own settings.

## Commands

- Install: `npm install`
- Local run: `npm run dev`
- Terminal UI (needs the bot running with `ENABLE_TUI=true`): `npm run tui`
- Lint: `npm run lint`
- Typecheck: `npm run typecheck`
- Unit tests: `npm test`
- Install/remove the systemd `--user` unit: `npm run systemd:install` / `npm run systemd:uninstall`
- Control the running service: `npm run systemd:start` / `systemd:stop` / `systemd:restart` / `systemd:status`
- Tail logs: `npm run logs` (`journalctl --user -u pi-bot -f`)

Before finishing code changes, run:

```bash
npm run verify
```

That runs `npm run lint`, then `npm run typecheck`, then `npm test`, then `npm run smoke` (imports every module, loads the extensions through Pi's loader, registers every tool, validates env/model config). It is the same gate `/restart` and the `restart_bot` tool use, so a failure there blocks restarts — keep tests fast and free of network or filesystem dependencies. Use `npm run format` to apply Biome formatting; `npm run lint` reports rule violations, which Biome does not fix automatically.

Keep `npm run lint` at zero errors. It went unchecked for a while because no script invoked it, and violations accumulated silently in `src/`.

## Tests

- `tests/` holds unit tests run by Node's built-in runner (`node --test`); there is no test framework dependency. Name files `*.test.ts`.
- Tests must live in `tests/`, not `src/`: `scripts/smoke.ts` imports every `.ts` file under `src/`, subdirectories included, and would execute them during the smoke check. Modules under `src/` must therefore be safe to import: no side effects beyond defining things.
- Coverage centres on the pure Telegram HTML machinery in `src/channels/telegram/telegram-html.ts` (escaping, sanitizing, tag-aware splitting) and the Markdown converter (`tests/telegram-markdown.test.ts`, by invariants: only Telegram's tags, balanced, content kept, every chunk sendable) — the code where a regression is silent because Telegram rejects a whole message on malformed markup — plus the prompt queue and the core (checked against `tests/recording-channel.ts`, a fake channel that records events and returns scripted receipts), the menu registry, the agent's delivery tools (against a fake tool host), the Telegram channel's send order, menus, uploads, job messages and its mirror of other channels' input, the terminal UI's socket (JSONL framing, the socket channel and server against `tests/scripted-core.ts`, `RemoteCore` against the real server half over in-memory streams), the terminal's views rendered off-screen, the session event hook, steering, the SDK's retries, the chat's transcript pointer, the background-work tools and their live progress messages (the core's job events drive Telegram's renderer, with its fetch mocked), session notes, cron storage, the callback menus, the Telegram transport, and the import boundary. Sub-agent tools are tested against a fake extension API with a fake worker (`tests/subagent.test.ts`); nothing in `tests/` may start a real Pi session.
- Prefer invariants over golden strings for the splitter (chunk fits the limit, chunk is independently balanced, no tag or entity cut in half, content preserved). They survive refactors and catch the failure modes that matter.

## Coding conventions

- TypeScript ESM project (`"type": "module"`) using `NodeNext` module resolution.
- Include explicit `.ts` extensions in local TypeScript imports.
- Keep strict TypeScript compatibility; avoid `any` unless there is a clear boundary reason.
- Match `biome.json`: 2-space indentation, single quotes, semicolons, 100-char lines.
- Prefer small, focused modules and typed helper functions.
- Preserve long-running bot behavior: do not block the polling loop, and keep Telegram/typing/file operations best-effort where appropriate.

## Environment and secrets

- Never commit `.env` or real API keys/tokens.
- Keep secrets and deployment-specific values in `.env`, such as `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_CHAT_ID`, provider API keys, optional ElevenLabs/Tavily API keys, `HEARTBEAT_MODEL` (required when the heartbeat is on), `CONTEXT_GIST_URL`, and the `ENABLE_SUBAGENTS` and `ENABLE_TUI` switches (both off by default; any value other than `true`/`false` is a startup error). `.env.example` documents each one.
- Non-secret bot configuration lives in `src/config.ts`, including chat/model choices, queue/timeouts, upload behavior, and heartbeat interval. The exception is runtime state in `files/settings.json`: the active model/reasoning level, Pi's `"cacheWarming"` (written as `"streaming"`, Pi's default, so a new default in a Pi upgrade cannot change what the bot spends unnoticed) and `"retry"` (`maxRetries` 4, one more than Pi's default, for a transient model error), `"heartbeat"` and `"cronJobs"` (both default `false`, both gating the ways the bot acts unprompted), and Telegram's display preferences `"toolCalls"`, `"showTranscripts"` and `"subagentToolCalls"` (set by its own commands `/toolcalls`, `/transcripts` and `/subagent_toolcalls`). That file belongs to Pi's `SettingsManager`, which merges writes into the existing contents, so bot-only keys added there survive `/models` and `/reasoning` — but they must be read through `BotSettings` in `src/config.ts`, not by re-reading the file elsewhere. `files/settings.json` itself is gitignored; `files/settings.json.example` is checked in and must stay byte-identical to what `ensureBotSettingsFile()` writes, so update both together when adding a key. Concurrency limits, timeouts, TTLs, and payload caps for background runs and background jobs (background bash, sub-agents) belong in its "Background work" section — do not add them as module-local constants. Telegram's API limits, its display settings and its pacing intervals (`TOOL_CALL_*`, `JOB_PROGRESS_*`) are in the "Telegram" section, and what applies to every channel (`ACTIVE_WINDOW_MS`, `CHANNEL_DRAIN_TIMEOUT_MS`) and the terminal UI's socket (`tuiSocketPath()`, `TUI_*`) in "Interfaces". Only narrow display widths stay next to the formatter that uses them.
- Provider-specific auth such as `OPENROUTER_API_KEY` or Pi auth storage is required for the selected model.

## Operational notes

- This bot uses Telegram long polling, not webhooks.
- Only one running process should poll a given Telegram bot token.
- Persistent app state lives under `files/`; avoid deleting or rewriting it unless explicitly requested. Chat transcripts live in `sessions/`. Every chat transcript shares the ID `chat-<chatId>`; startup resumes the one `sessions/current-chat` names. A new conversation writes its transcript's path there as it starts, and `/new` and `start_new_session` delete the file. The background session is session-per-prompt (`PiRuntime.sessionPerPrompt`): every run starts a fresh transcript with its own ID, and nothing carries over between runs. Heartbeat runs go to `sessions/heartbeat-sessions/` (`heartbeat-<chatId>-<random>`), scheduled-task runs to `sessions/scheduled-tasks-sessions/` (`scheduled-task-<chatId>-<random>`, named after the task); `backgroundRunTranscript` in `src/prompt-queue.ts` picks which. A background-bash or sub-agent job started from a background run records that run's transcript in its `JobOrigin`, and its completion report resumes that transcript (`IncomingPrompt.resumeSessionFile`); an interrupted-jobs note at shutdown is likewise written to each originating run's transcript. The SDK writes a new transcript to disk only with its first assistant message, so a restart before then finds nothing at that path and starts fresh. Sub-agent worker transcripts under `sessions/subagent-sessions/` are kept indefinitely; each records its parent's transcript path in the session header and a `pi-bot-subagent` custom entry with the job, task, tool call, and parent leaf entry. `TELEGRAM_ALLOWED_CHAT_ID` in `.env` is the single Telegram chat allowed to use the bot; every other chat is ignored.
- Temporary downloads/generated files are under the system temp directory.
- With `ENABLE_TUI=true` the bot listens on `$XDG_RUNTIME_DIR/pi-bot/tui.sock` (or `/run/user/<uid>/pi-bot/`, else `<tmp>/pi-bot-<uid>/`), directory `0700` and socket `0600`; `npm run tui` finds the same path. A socket that will not open is logged and announced, and Telegram carries on without it.
- After changing extensions, prompts, or env vars, restart the bot.
- Deployment is a systemd `--user` unit written by `scripts/systemd.sh` to `~/.config/systemd/user/pi-bot.service`. It is generated, not checked in: change the script, then re-run `npm run systemd:install`. `Restart=always` is what makes `/restart` and `restart_bot` work — both exit 0 on purpose and rely on the supervisor to bring the process back.

## Pi-specific work

When modifying Pi SDK usage, extensions, themes, TUI code, or Pi agent behavior, consult the installed Pi documentation/examples before implementing. Follow existing project patterns in `src/pi-session.ts`, `src/system-prompt.ts`, and `extensions/`.
